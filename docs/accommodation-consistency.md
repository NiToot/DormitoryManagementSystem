# 第三阶段：住宿分配与调宿一致性

## 写入协议

保留 dorm_room 的四床位结构。所有住宿分配、退宿、房间修改/删除、调宿提交/编辑/审批/删除以及学生删除、楼宇编号变更/删除，在 Spring READ_COMMITTED 事务内先取得 accommodation_lock 中 id=1 的数据库行锁。锁保持至提交或回滚，因此不同进程也不能绕过彼此的“先检查、再写入”步骤。所有业务失败以异常结束，不能捕获异常后仍提交半条业务。

当前选择串行住宿写事务，读列表不取得这把写锁。它减少现有模型改动，便于验证，但写吞吐受单行锁限制；规模增长后应改成规范化床位/入住表、唯一约束与按学生和房间有序加锁。该协议保护本应用的写入入口，不是四个床位字段之间的数据库 UNIQUE 约束；运行旧版本后端或直接执行外部 SQL 都可能破坏保证，应停机维护并重新检查数据。

房间和申请都有 version，列表响应携带版本。更新房间、编辑/审批申请时在 JSON 中回传 version；房间/床位/申请删除在 query 中传 version。缺失或过期返回 HTTP 409。前端会提示冲突、关闭过期表单并重新读取列表，不自动覆盖或重试。

## 入住和退宿规则

- 学生必须存在，学号按数据库主键规范化后校验；同一个人不能占同房两床，也不能同时出现在不同房间。
- 房间容量为 1–4，床位编号不得超出容量，楼宇必须存在；实际人数始终根据床位计算，客户端人数只作兼容字段，不参与决策。
- 普通房间更新可修改有效结构信息和向空床分配学生，不能直接把已占床位换成另一个人。需要先退宿或办理调宿；占用房间不能直接换楼。
- 退宿使用当前房间版本；重复退空床或旧页面重复请求返回 409，不减成负数。
- 已入住房间、涉及待处理调宿的房间不能删除；未退宿或有待处理调宿的学生不能删除。楼宇仍有房间、宿管、报修或访客引用时不能删除或改编号。
- 沿用第二阶段权限：管理员全局，宿管本楼；未分配学生由管理员分配。跨楼调宿由管理员审批。

## 调宿规则

每名学生最多一个待处理申请。提交时按当前会话推导申请人、原房间和原床位；编辑只允许本人未处理申请的目标房间/床位。申请创建不预占目标床位，最终是否可用由审批事务重新检查。

审批读取数据库中的原申请和版本，不信任请求体中的原床位、目标、申请人等字段。通过审批时确认原床位仍属于申请人、目标在有效容量内且空闲、学生没有重复入住。随后在同一事务内清除原床位、填入目标床位、重新计算两房人数、递增版本、写申请状态和完成时间。任何一步失败，全部回滚。同房换床只更新房间一次，人数不变。

同一申请并发审批只能成功一次；两人争同床时失败者保留原床位与待处理状态。编辑与审批争同一版本时只有一个成功。已处理申请不能重复审批、编辑或删除，保留状态记录供追溯。

## 数据库升级

全新库直接导入 database/init.sql，共 10 张表（原 9 张业务表加 1 张协调锁表）。第二阶段已有演示库先停止旧后端、备份，再从仓库根目录运行：

```powershell
mysql --host=127.0.0.1 --port=13306 --user=root --password --execute="SOURCE database/003-accommodation.sql"
```

第一阶段旧库还需先按 security-baseline.md 完成 002-security.sql 与密码迁移。初始化文件不会 ALTER 已有表，不能代替增量迁移。

003 SQL 幂等增加锁表及两个 version 字段，并输出历史重复入住和重复待处理申请供核查，不删除或猜测修复数据。新后端启动时还会检查学生/楼宇引用、容量和人数；冲突数据会阻止启动，需要停机核实后再重启。维护时不要同时运行旧后端，应用账号无需额外 DDL 权限，只需专用演示库的既有 DML 权限。

## 本地验证方式

按 README 配置专用 dormitory_demo 后，在后端执行 Maven test。AccommodationTests 使用事务回滚；AccommodationConcurrencyTests 刻意不用测试外层事务，创建虚构的 99970001–99970004 学生和 9700–9703 房间，使用两个线程、两个独立会话和真实数据库连接竞争，然后清理测试记录。

并发测试验证同床竞争、同学生多房、同申请重复审批、两申请争同床、审批与编辑竞争、重复待处理申请。故障测试在实际写入两个房间后注入异常，再查询数据库确认房间、人数、版本和申请状态全部回滚。另覆盖同房换床、原床位变化、目标容量、历史冲突启动检查。该测试不是吞吐基准或生产压力测试。
